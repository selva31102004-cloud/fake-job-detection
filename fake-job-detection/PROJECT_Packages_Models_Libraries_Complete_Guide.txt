SECTION 1 — WHAT IS THIS PROJECT?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FraudShield (also called JobGuard AI) is a full-stack AI-powered web application that
detects fake and fraudulent job postings. It protects job seekers from scams,
phishing, and data theft disguised as legitimate job offers.

PROBLEM IT SOLVES:
  Millions of fake job postings appear online every year, tricking people into:
  → Paying upfront "registration fees" or "training fees" (money scam)
  → Submitting personal info like SSN, bank account, passport (identity theft)
  → Wasting time applying to non-existent companies
  → Falling victim to work-from-home envelope-stuffing scams

HOW IT WORKS (simple summary):
  1. User provides a job posting (as text, a URL, or a screenshot image)
  2. The system extracts and cleans the text
  3. A hybrid AI model analyzes the text for fraud signals
  4. Returns: FAKE or REAL prediction + confidence score + reasons + recommendations

WHAT IT IS:
  Uvicorn is an ASGI (Asynchronous Server Gateway Interface) web server.
  It is the server that actually "runs" the FastAPI application.

WHY THIS PROJECT USES IT:

  In Docker, the CMD in the Dockerfile is:
    uvicorn main:app --host 0.0.0.0 --port 8000 --workers 2

─────────────────────────────────────────────────────────────────────
MODEL 1 — Random Forest Classifier (60% weight in final prediction)
─────────────────────────────────────────────────────────────────────
WHAT IS A RANDOM FOREST?
  A Random Forest is an ensemble of many decision trees.
  A decision tree is like a flowchart:
    "Is caps_ratio > 0.3?"  YES → more likely fake
    "Is word_count < 50?"   YES → more likely fake
    "Has company name?"     NO  → more likely fake

  A single tree can overfit (memorize training data).
  Random Forest fixes this by:
    → Building 150 separate trees
    → Each tree sees a random subset of training samples
    → Each split in a tree considers random subset of features
    → All trees vote — majority wins

CONFIGURATION IN THIS PROJECT:
  RandomForestClassifier(
      n_estimators=150,      # 150 trees in the forest
      max_depth=8,           # each tree can be at most 8 levels deep
      random_state=42,       # reproducible results
      class_weight="balanced" # adjusts for the fact that fake jobs are
  )                           # rarer than real jobs in training data

WHAT FEATURES IT ANALYZES:
  The 17 structured features extracted per job posting:
    1.  word_count             — total word count
    2.  has_description        — is there a description? (1/0)
    3.  has_requirements       — are requirements listed? (1/0)
    4.  has_company_name       — is company named? (1/0)
    5.  has_salary             — is salary mentioned? (1/0)
    6.  has_location           — is location given? (1/0)
    7.  has_job_title          — is title present? (1/0)
    8.  exclamation_count      — how many "!" in the text
    9.  caps_ratio             — % of letters that are UPPERCASE
    10. dollar_sign_count      — how many "$" symbols
    11. email_count            — number of email addresses found
    12. url_count              — number of URLs found
    13. suspicious_score       — weighted count of fraud keywords found
    14. legitimacy_score       — count of legitimate indicator phrases
    15. from_trusted_source    — posted on LinkedIn/Indeed/etc? (1/0)
    16. avg_sentence_length    — average words per sentence
    17. has_proper_punctuation — uses periods/commas? (1/0)

WHY RANDOM FOREST FOR THIS TASK?
  → Handles mixed feature types (numeric scores + binary flags) naturally
  → Robust to outliers and noisy features
  → Can capture non-linear patterns (e.g., HIGH caps_ratio AND
    many exclamation marks together = very suspicious)
  → class_weight="balanced" handles the imbalanced dataset
    (real jobs far outnumber fake ones)

─────────────────────────────────────────────────────────────────────
MODEL 2 — Logistic Regression (40% weight in final prediction)
─────────────────────────────────────────────────────────────────────
WHAT IS LOGISTIC REGRESSION?
  Logistic Regression is a linear classification model.
  It learns a weighted combination of all input features, then
  passes it through a sigmoid function to output a probability
  between 0 and 1.

  Formula: P(FAKE) = sigmoid(w1*feature1 + w2*feature2 + ... + bias)
  sigmoid(x) = 1 / (1 + e^(-x))  → outputs 0 to 1 (probability)

CONFIGURATION IN THIS PROJECT:
  LogisticRegression(
      max_iter=1000,         # run up to 1000 optimization steps
      C=1.0,                 # regularization strength (prevents overfitting)
      class_weight="balanced", # handles imbalanced classes
      solver="lbfgs",        # Limited-memory BFGS optimizer (good for small data)
      random_state=42        # reproducible
  )

WHY LOGISTIC REGRESSION ALONGSIDE RANDOM FOREST?
  → Linear models capture global linear relationships between features
  → Complements Random Forest which captures non-linear interactions
  → Very interpretable — you can see which features get highest weights
  → Less likely to overfit on small training data
  → The two models together (ensemble) are more accurate than either alone

─────────────────────────────────────────────────────────────────────
MODEL 3 — TF-IDF Vectorizer (Text NLP Features)
─────────────────────────────────────────────────────────────────────
WHAT IS TF-IDF?
  TF-IDF = Term Frequency - Inverse Document Frequency.
  It converts text into a numerical matrix where each column represents
  a word or phrase, and each value represents how important that
  word/phrase is in a given document.

  TF  (Term Frequency) = how often a word appears in this job posting
  IDF (Inverse Doc Frequency) = how rare the word is across all postings
  → Common words like "the", "and" get low scores (high IDF penalty)
  → Rare but meaningful words like "registration fee" get high scores

CONFIGURATION IN THIS PROJECT:
  TfidfVectorizer(
      ngram_range=(1, 2),    # single words AND two-word phrases
      max_features=500,      # keep only top 500 most important terms
      sublinear_tf=True      # use log(1 + tf) instead of tf to reduce
  )                           # the dominance of very frequent words

WHY BIGRAMS (ngram_range=(1,2))?
  Many fraud phrases are two words:
    "registration fee", "easy money", "work from home",
    "anyone can", "no experience", "guaranteed income"
  
  A single-word model would miss these. Bigrams capture them perfectly.

HOW IT COMBINES WITH THE ML MODELS:
  The 500 TF-IDF text features are combined (horizontally stacked)
  with the 17 structured numeric features to create one combined matrix:

    X_combined = [17 structured features | 500 TF-IDF features]
                  = 517 total features per job posting

  Both Random Forest and Logistic Regression are trained on this
  517-feature combined input.

─────────────────────────────────────────────────────────────────────
MODEL 4 — VotingClassifier (Ensemble Combiner)
─────────────────────────────────────────────────────────────────────
WHAT IS AN ENSEMBLE?
  An ensemble combines multiple models to produce a better prediction
  than any single model could achieve alone.

SOFT VOTING (used here):
  Each model outputs a probability: e.g., RF says 0.82, LR says 0.74
  The ensemble averages them with weights: 0.6 × 0.82 + 0.4 × 0.74 = 0.788
  Final prediction: FAKE (above 0.5 threshold)

HOW THE WEIGHTS WORK:
  Random Forest  → weight 0.6  (more complex, usually more accurate)
  Logistic Reg.  → weight 0.4  (simpler, good complement)

  Final score shown to user:
    ensemble score = weighted average of RF and LR probabilities

─────────────────────────────────────────────────────────────────────
RULE-BASED KNOWLEDGE BASE (NLP Pattern Matching — 70+ patterns)
─────────────────────────────────────────────────────────────────────
WHAT IT IS:
  A handcrafted dictionary of 70+ known fraud keyword patterns,
  organized into 7 categories with different risk weights.

WHY USE RULES ALONGSIDE ML?
  → ML models generalize from training data but may miss specific
    new phrases not seen in training
  → Rules are 100% explainable — you can show the user exactly
    which keywords triggered the alert
  → Rules provide the "reasons" shown in the explanation panel

THE 7 FRAUD CATEGORIES AND THEIR PATTERNS:

  CATEGORY 1: PAYMENT REQUIRED (weight 1.0 — highest risk)
    Keywords: "registration fee", "training fee", "deposit required",
    "pay to work", "investment required", "startup fee",
    "application fee", "processing fee", "background check fee",
    "kit fee", "equipment fee"
    Why weight 1.0: Legitimate employers NEVER ask workers to pay money.
    Any fee request is almost certainly a scam.

  CATEGORY 2: UNREALISTIC SALARY (weight 0.9 — very high risk)
    Keywords: "earn $5000 weekly", "make $10000 a week", "unlimited income",
    "guaranteed income", "$500 per day", "$3000 per day",
    "earn 50000 monthly", "$10000 a week", "earn thousands"
    Why: Real salaries are specific and reasonable. Scams use
    exaggerated income claims to attract desperate job seekers.

  CATEGORY 3: URGENCY PRESSURE (weight 0.8 — high risk)
    Keywords: "urgent", "immediate", "asap", "right now", "today only",
    "limited time", "act fast", "don't wait", "hurry", "apply immediately"
    Why: Manufactured urgency prevents rational thinking.
    Legitimate hiring processes take days or weeks — not minutes.

  CATEGORY 4: SUSPICIOUS COMPANY INFO (weight 0.75 — high risk)
    Keywords: "newly established", "startup opportunity",
    "anonymous employer", "confidential company", "name withheld",
    "undisclosed company"
    Why: Legitimate employers always identify themselves.
    Hidden identity = hiding something.

  CATEGORY 5: POOR QUALITY INDICATORS (weight 0.7 — medium-high risk)
    Keywords: "!!!!", "$$$$", "click here now", "100% guaranteed",
    "risk free", "no risk", "secret method", "proven system"
    Why: Excessive punctuation, guarantees, and "secret methods"
    are classic marketing scam language, not professional job listings.

  CATEGORY 6: VAGUE DESCRIPTION (weight 0.6 — medium risk)
    Keywords: "easy money", "work from home", "be your own boss",
    "flexible hours", "no experience required", "anyone can do it",
    "simple tasks", "data entry from home", "envelope stuffing",
    "click ads"
    Why: Real jobs describe specific duties. Vague descriptions
    hide the fact that no real job exists.

  CATEGORY 7: PERSONAL INFO REQUESTS (weight 1.0 — highest risk)
    Keywords: "send bank details", "provide ssn", "social security",
    "wire transfer", "western union", "money gram", "send passport",
    "credit card number", "bank account", "routing number"
    Why: No employer needs your bank account or passport
    during a job application. This is identity theft.

LEGITIMATE INDICATORS (used to reduce fraud score):
  "equal opportunity employer", "background check required",
  "drug test", "competitive benefits", "health insurance", "401k",
  "pto", "paid time off", "university degree", "bachelor's",
  "master's", "years of experience", "interview process",
  "hr department", "onboarding", "performance review",
  "team environment", "career growth", "professional development"

TRUSTED PLATFORM BONUS:
  If the job URL comes from these domains, the legitimacy score rises:
  linkedin.com, indeed.com, glassdoor.com, monster.com,
  careerbuilder.com, ziprecruiter.com, dice.com, greenhouse.io,
  lever.co, workday.com, bamboohr.com, jobvite.com

─────────────────────────────────────────────────────────────────────
FALLBACK RULE-BASED PREDICTOR
─────────────────────────────────────────────────────────────────────
If scikit-learn is not installed (e.g., running on minimal system),
a mathematical rule-based fallback runs instead:

  raw_score = suspicious_score × 0.25
            - legitimacy_score × 0.08
            + missing_fields   × 0.07

  fake_probability = sigmoid(raw_score)
                   = 1 / (1 + e^(-raw_score))

This is shown to the user as "Rule-Based Fallback" instead of
"Trained ML (RF + LR Ensemble)".

SECTION 6 — BACKEND MODULES (FILE-BY-FILE EXPLANATION)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

FILE: backend/main.py
  → FastAPI app initialization
  → CORS middleware (allows browser on port 3000 to call port 8000)
  → Imports and registers two routers:
      router (api/routes.py) — analysis endpoints
      auth_router (api/auth.py) — login/register endpoints
  → On startup: calls init_db() to create MySQL tables if missing
  → Entry point: uvicorn.run("main:app", host="0.0.0.0", port=8000)

FILE: backend/api/routes.py
  → Defines 4 HTTP endpoints:
      POST /analyze/image → image → OCR → preprocess → detect → response
      POST /analyze/url   → url → scrape → detect → response
      POST /analyze/text  → text dict → detect → response
      GET  /model/stats   → returns accuracy, precision, recall, F1
  → All endpoints use Pydantic for input validation
  → All call detector.analyze(job_data) at their core

FILE: backend/api/auth.py
  → User authentication system
  → REGISTER: hashes password with SHA-256 + random salt → INSERT to MySQL
  → LOGIN: verifies hashed password → creates JWT token → returns token
  → VERIFY TOKEN: JWT decode + expiry check for protected routes
  → Two token TTLs: 24h (standard) / 30 days (remember me)
  → Password hashing uses hashlib.sha256 with a random 32-byte salt
    (salt prevents rainbow table attacks)

FILE: backend/models/detector.py
  → The core AI engine. Contains:
      TRAINING_SAMPLES: 35 labeled job postings (built-in training data)
      SUSPICIOUS_KEYWORDS: 70+ fraud patterns in 7 categories
      LEGITIMATE_INDICATORS: 19 phrases that signal a real job
      TRUSTED_DOMAINS: 12 legitimate job platform domains

      FeatureExtractor class: converts job dict → 17 numeric features
      _train_and_save(): trains RF + LR + TF-IDF, saves to .pkl
      _load_or_train(): loads existing model or trains new one
      ExplainabilityEngine class: generates reasons/explanations
      FakeJobDetector class: main analyzer — calls all above

FILE: backend/utils/preprocessor.py
  → Converts raw text (from OCR) or a URL-scraped dict into a
    standardized job_data dictionary
  → Uses regex to extract salary patterns, email addresses, phone
    numbers, job title, company name, location from unstructured text
  → Extracts "Requirements" section if it exists
  → Builds full_text by concatenating all fields

FILE: backend/utils/ocr.py
  → Tries pytesseract (Tesseract OCR) first
  → Falls back to easyocr if Tesseract not available
  → Falls back to image metadata if both fail
  → Preprocesses image with Pillow: grayscale → enhance contrast → sharpen
  → Cleans OCR output: removes excessive whitespace, OCR artifacts,
    normalizes smart quotes

FILE: backend/utils/scraper.py
  → Fetches job posting page HTML using requests
  → Parses with BeautifulSoup4 using CSS selectors
  → Domain-specific scrapers for: LinkedIn, Indeed, Glassdoor
  → Generic scraper: tries schema.org JSON-LD first, then heuristic
    CSS patterns (h1, .job-title, .company-name, etc.)
  → Fallback: analyze_url_only() — if scraping fails, at least check
    if the domain is a trusted source

FILE: backend/models/trained_model.pkl
  → Pre-trained model file serialized with Python's pickle module
  → Contains: {"ensemble": VotingClassifier, "tfidf": TfidfVectorizer}
  → Auto-regenerated if missing or corrupt on next startup
  → Size: ~350KB (small — only 35 training samples)

FILE: backend/db_setup.sql
  → SQL script to create the login_system database and users table
  → Run once before first backend startup
  → In Docker: auto-runs via docker-entrypoint-initdb.d mount

FILE: backend/train_on_emscad.py
  → Script to retrain on the full EMSCAD dataset (17,880 samples)
  → Loads CSV, maps columns to FeatureExtractor format
  → Trains same RF + LR + TF-IDF pipeline
  → Runs cross-validation and prints classification report
  → Saves new trained_model.pkl (replaces the 35-sample version)

─────────────────────────────────────────────────────────────────────
WHAT IT IS:

SECTION 9 — SECURITY DESIGN
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

PASSWORD SECURITY:
  → Passwords are NEVER stored in plain text
  → A random 32-byte salt is generated per user using secrets.token_hex(32)
  → Password is hashed: sha256(salt + password).hexdigest()
  → Salt is stored alongside the hash — needed to verify on login
  → Even if the database is leaked, passwords cannot be reversed

JWT TOKEN SECURITY:
  → Signed with HS256 (HMAC-SHA256) using JWT_SECRET
  → Contains: user_id, email, expiry (exp)
  → Server verifies signature on every protected request
  → Cannot be forged without the secret key

CORS CONFIGURATION:
  → allow_origins=["*"] is used — suitable for development
  → For production: restrict to specific frontend domain only

SECTION 11 — WHY EACH DESIGN DECISION WAS MADE
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

WHY FASTAPI INSTEAD OF FLASK OR DJANGO?
  → FastAPI is 2–3× faster than Flask for I/O-heavy workloads
  → Auto-generates /docs Swagger page (great for testing and demos)
  → Native async support handles concurrent image/URL analysis better
  → Pydantic integration provides automatic input validation

WHY RANDOM FOREST + LOGISTIC REGRESSION INSTEAD OF DEEP LEARNING?
  → Training data is only 35 samples built-in (BERT needs thousands)
  → RF and LR train in milliseconds; BERT takes hours
  → These models are explainable — feature importances are available
  → No GPU required — runs on any laptop
  → Accuracy is still high when combined with good NLP features

WHY MYSQL INSTEAD OF SQLITE OR POSTGRESQL?
  → MySQL is widely taught in academic projects
  → Easy to manage with GUI tools like MySQL Workbench / phpMyAdmin
  → Good Docker image availability
  → Production-ready for scaling

WHY HYBRID (ML + RULES) INSTEAD OF PURE ML?
  → Pure ML is a black box — users can't see why something is "fake"
  → Rule-based patterns provide human-readable explanations
  → Rules catch brand-new scam phrases not seen in training data
  → ML catches subtle patterns rules would miss
  → Together they provide better accuracy AND explainability

WHY TF-IDF INSTEAD OF WORD2VEC OR BERT?
  → TF-IDF is interpretable — specific terms can be highlighted
  → No pre-trained model download needed (self-contained)
  → Works well on short texts like job postings (< 500 words)
  → Bigrams capture multi-word fraud phrases ("registration fee")
  → BERT would require 400MB+ model download and GPU

WHY NGINX AS FRONTEND SERVER?
  → Nginx is extremely fast for static file serving
  → Acts as reverse proxy so frontend and backend share port 3000
  → The same nginx.conf works in both development and production
  → Alpine image is tiny (5MB) — minimal Docker overhead
